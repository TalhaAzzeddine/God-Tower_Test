# God Tower – Unity Technical Test

## Overview

This project is a Unity reproduction of the reference **God Tower** climbing game provided for the Mid/Senior Unity Developer technical test.

The goal of the implementation was to reproduce the reference's core climbing loop, mobile controls, tower progression, presentation, and the required webhook-triggered bump event while keeping the implementation lightweight and suitable for Android.

### Project / Build

- **Unity Version:** 6000.4.1f1
- **Render Pipeline:** Universal Render Pipeline (URP)
- **Target Platform:** Android APK
- **Project / Test:** `God_Tower_Test`
- **Camera:** Orthographic / Cinemachine follow
- **Input:** Unity Input System

---

## Gameplay

The player controls a climbing character using two on-screen buttons:

- **Up:** climb upward

The climbing system uses smooth vertical movement combined with IK hand reaching and hanging behavior. When the player releases a climb input after a hand has reached a grab position, the hand remains in the climbing pose. Pressing the direction again continues the unfinished climbing action.

The game does not use a traditional death state. The player can continue climbing up and down within the tower limits. The main completion condition is reaching the top of the current tower.

### Player states / behavior

- Idle
- Climbing up
- Climbing down
- Hand reach / grab
- Hanging from a reached hand
- Bump reaction
- Level completion sequence

## Levels

The project contains exactly **5 playable levels** with progressive tower height and increasing challenge.

| Level | Tower Columns | Difficulty |
|---|---:|---|
| Level 1 | 10 | Intro / Easy |
| Level 2 | 20 | Medium |
| Level 3 | 25 | Challenging |
| Level 4 | 30 | Hard |
| Level 5 | 40 | Final Challenge |

Tower columns are generated by the tower spawning system. The player climb limits are automatically configured from the generated tower height.

### Level completion

When the player reaches the top of the tower:

1. Normal gameplay is stopped.
2. Up control are disabled.
3. A short victory sequence is played using the bump/glove effect from above.
4. After the sequence, the completion / Game Over UI is displayed.
5. The UI provides a **Main Menu** button and **Next Level/Replay** button.

The completion flow is intentionally handled by the gameplay setup/level flow code, while the bump system is responsible only for the bump/glove effect itself.

## Webhook – `/bump`

The build exposes a local HTTP endpoint while gameplay is running:

```text
GET  http://localhost:56789/bump
POST http://localhost:56789/bump
```

Example:

```bash
curl -X POST http://localhost:56789/bump
```

The endpoint is implemented using a lightweight **TCP listener** without an external web framework.

### Thread safety

HTTP requests are received on a background networking thread. Request results are placed into a thread-safe queue and consumed from Unity's main thread before any Unity scene/GameObject API is accessed.

This keeps the HTTP listener responsive while ensuring Unity objects are only modified from the main thread.

### Bump behavior

When `/bump` is triggered during gameplay:

- A random bump direction is selected.
- A burst of **4–6 boxing gloves** is spawned.
- Gloves spawn rapidly one-by-one.
- Each glove uses a different screen lane during the burst.
- For a bottom-to-top bump, gloves enter from below and travel vertically upward.
- For a top-to-bottom bump, gloves enter from above and travel vertically downward.
- Gloves hit the player's height, trigger impact VFX and SFX, affect the player's vertical position, and continue moving off-screen in the same vertical direction.
- Bottom impacts move the player upward.
- Top impacts move the player downward.
- Impact height is randomized within the configured range.
- The bump effect does not permanently disable gameplay; normal climbing can continue afterward.

## Testing the Webhook in Unity Editor

1. Open the project in Unity.
2. Enter **Play Mode**.
3. Make sure the game scene is running and the webhook listener has started.
4. Open **Command Prompt / PowerShell** on the same PC.
5. Run:

```bash
curl -X POST http://localhost:56789/bump
```

You should see the bump/glove event immediately in the running game.

You can also test the endpoint with GET:

```bash
curl http://localhost:56789/bump
```

### Editor debug controls

For faster iteration, the bump system also exposes editor test buttons and keyboard shortcuts while running in the Unity Editor:

- **B** → Bottom-to-Top bump
- **T** → Top-to-Bottom bump

These keyboard shortcuts are editor-only and are not included as gameplay controls in the Android build.

## Testing the Webhook on Android

The APK listens on `localhost:56789` on the Android device itself.

A PC cannot directly reach the Android device's localhost, so for a PC-side `curl` test use ADB port forwarding.

### 1. Verify the device

```bash
adb devices
```

The device should appear as `device`.

### 2. Forward the port

```bash
adb forward tcp:56789 tcp:56789
```

### 3. Start the APK

Launch the APK on the Android device and enter a playable level.

### 4. Trigger the bump from the PC

```bash
curl -X POST http://localhost:56789/bump
```

The event should play on the Android device.

### Verify the forwarding

```bash
adb forward --list
```

A mapping for port `56789` should be present.

### Why `adb forward` is used

For this implementation the request direction is:

```text
PC terminal / curl
        ↓
PC localhost:56789
        ↓
ADB port forwarding
        ↓
Android localhost:56789
        ↓
Unity APK
```

Therefore `adb forward` is the appropriate command for PC-side testing of the Android-local HTTP listener.

## Project Structure

The main systems are separated by responsibility:

```text
Scripts/
├── Player/
│   ├── ClimberController
│   ├── ClimberInput
│   └── GokuClimbingController
│
├── Tower/
│   ├── TowerSpawner
│   └── TowerGameplaySetup
│
└── Webhook/
    ├── WebhookListener
    └── BumpEventController
```

### Main responsibilities

**ClimberController**

Owns player vertical movement, movement limits, climbing steps, and bump displacement.

**GokuClimbingController**

Owns the visual climbing/IK behavior, hand reaching, grabbing and hanging presentation.

**TowerSpawner**

Builds the tower from reusable column prefabs and places the tower top section.

**TowerGameplaySetup**

Initializes the current tower, configures climb limits, detects level completion, controls the victory sequence, and owns the completion UI flow.

**BumpEventController**

Owns the glove event, glove spawning/animation, impact VFX, impact SFX, camera shake, and vertical bump effect. It does not own the Game Over / completion UI.

**WebhookListener**

Owns the local HTTP listener and safely dispatches webhook events to the Unity main thread.

## Performance / Technical Notes

- Target platform is Android.
- The project uses URP.
- The climbing and bump systems use lightweight coroutine-based movement.
- The webhook listener uses a minimal TCP listener rather than an external HTTP framework.
- Webhook requests are dispatched to Unity's main thread through a thread-safe queue.
- Tower columns are spawned procedurally from reusable prefabs.
- Gloves and impact VFX are spawned only when the relevant event occurs.
- The bump event is designed to be temporary and recover cleanly so the player can continue playing afterward.

## Build & Submission

The technical-test deliverables are:

1. **Android APK** – playable build containing all 5 levels and the webhook event.
2. **Gameplay video** – showing the main menu, some levels being played/completed, and the webhook bump event.
3. **Unity project source** – clean project excluding generated folders such as `Library/`, `Temp/`, and `Build/`.





## Notes / Assumptions

- The reference is reproduced as a new Unity implementation rather than a pixel-perfect copy of the original assets.
- The project prioritizes gameplay feel, camera framing, mobile usability, tower progression, and the required webhook event within the technical-test time constraint.
- The webhook event is intentionally implemented as an independent gameplay effect so it can be triggered externally without coupling the HTTP layer directly to the player controller.
- The completion state is reached by climbing to the top of the tower; there is no conventional player death state in the implemented gameplay loop.
